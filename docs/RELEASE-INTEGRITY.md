# Release integrity

Pinned-binary integrations should download GitHub Release assets directly and
verify the complete evidence set before executing the binary. `install.sh` and
`cargo install git-std` remain standalone convenience flows for human use.

## Targets and asset set

| Platform            | Target                       |
| ------------------- | ---------------------------- |
| Linux x86-64        | `x86_64-unknown-linux-musl`  |
| Linux ARM64         | `aarch64-unknown-linux-musl` |
| macOS x86-64        | `x86_64-apple-darwin`        |
| macOS Apple Silicon | `aarch64-apple-darwin`       |
| Windows x86-64      | `x86_64-pc-windows-msvc`     |

For every target, a release publishes this inseparable set:

```text
git-std-<target>.tar.gz
git-std-<target>.tar.gz.sha256
git-std-<target>.tar.gz.sigstore.json
git-std-<target>.tar.gz.spdx.json
git-std-<target>.tar.gz.provenance.sigstore.json
```

The archive contains `git-std` (`git-std.exe` for Windows) and generated man
pages at its root. The checksum names the exact archive bytes. The SPDX 2.3
document records the archive name, release version, and SHA-256 digest. The
signature bundle is a keyless Sigstore blob signature. The provenance bundle is
generated by GitHub artifact attestations with the archive as its subject.

## Local verification

Local verification is offline and does not establish signer identity:

```bash
scripts/release/verify.sh git-std-<target>.tar.gz vX.Y.Z
```

It checks the allowed target name, archive layout, checksum, SPDX version and
subject data, and JSON shape/presence of both Sigstore bundles. The release test
suite proves success and rejection of altered bytes, checksums, SBOM metadata,
and missing bundles:

```bash
just test-release
```

## Hosted verification

Hosted verification additionally checks the transparency-log certificate and
GitHub provenance identity:

```bash
scripts/release/verify.sh git-std-<target>.tar.gz vX.Y.Z --hosted
```

This invokes `cosign verify-blob` with the exact repository workflow identity at
`refs/tags/vX.Y.Z`, and `gh attestation verify` with the saved provenance bundle
and the same source ref. It requires Cosign, GitHub CLI, network access, and
evidence generated by GitHub Actions. The unsigned SBOM version label alone does
not establish release identity; both cryptographic checks bind the requested tag.

For a nonpublishing workflow-dispatch build, explicitly select its branch ref:

```bash
scripts/release/verify.sh git-std-<target>.tar.gz vX.Y.Z \
  --hosted --source-ref refs/heads/qualification
```

This qualifies branch artifacts, not a published release. A different tag from
`refs/tags/vX.Y.Z` is rejected. CI passes its actual `GITHUB_REF` explicitly.
Use the current helper: the copy at tag `v0.12.1` accepts any ref of the release
workflow and can accept a relabelled SBOM. The strengthened helper rejects that
case while successfully verifying the original v0.12.1 assets.

The v0.12.1 release provides signed provenance generated by GitHub's hosted build
platform, verified for each exact archive and release ref. This meets the
[SLSA Build Level 2 provenance model][slsa-build]; it is a project assessment,
not an independent certification or a Build Level 3 claim.

[slsa-build]: https://slsa.dev/spec/v1.2/build-track-basics

## Real-release verification

A real-release check confirms facts local tests cannot:

1. all five jobs cross-build successfully;
2. OIDC keyless signing and transparency-log inclusion succeed;
3. GitHub stores and verifies each provenance attestation;
4. the GitHub Release exposes all 25 expected files without renaming; and
5. downloaded bytes pass hosted verification independently.

Manual `workflow_dispatch` runs build and evidence generation but never create
a Release or publish crates. Only a `v*` tag enables those jobs.

Release `v0.12.1` publishes all 25 files for the five targets above. The
[release workflow][qualified-run] passed all five builds and smoke jobs. On
2026-11-18, all five downloaded archives passed the strengthened hosted verifier,
including checksum, archive layout, SBOM subject, exact signature identity, and
provenance source-ref verification. A genuine archive relabelled as `v9.9.9` was
rejected by certificate identity verification. See the
[qualification record](FOLIO-QUALIFICATION.md) for archive digests and limits.

Release `v0.11.15` has archives and checksums but no enhanced companions. Failed
release `v0.12.0` is not the qualified asset baseline.

[qualified-run]: https://github.com/driftsys/git-std/actions/runs/43771684971

## Collecting generated man pages

Release builds capture Cargo JSON messages and match the `git-std` binary's
manifest to the workspace package. The collector uses that package's
`build-script-executed.out_dir` to locate generated man pages. It does not
search Cargo's private build directory layout, which changed in Cargo 1.100.
Custom target and build directories therefore do not require new globs.
For cross v0.2.5, the collector maps the container's `/target` and `/project`
mounts to the host directories reported by Cargo metadata.

Collection requires a successful build, one matching build-script output,
and the main `git-std.1` page. Missing or ambiguous outputs fail packaging;
other build directories cannot supply fallback pages. Previously staged
man pages are replaced. Signature, provenance, checksum, and smoke gates
remain required before publication.

Run `just test-release` for layout and rejection fixtures. Before publishing
a packaging correction, dispatch the release workflow on its reviewed branch
and require all five target builds and smoke jobs to pass. Manual dispatch
runs the integrity gates without creating a release or publishing crates.
